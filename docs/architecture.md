# 系统架构

## 1. 总体结构

项目采用单仓库组织，包含三个独立运行的应用和一组基础设施服务。

| 目录 | 技术栈 | 主要职责 |
| --- | --- | --- |
| `apps/api` | Go、Gin、GORM | HTTP API、鉴权、业务规则、数据持久化、对象存储、事件推送与审计 |
| `apps/worker` | Go、Redis Streams、Docker | 消费判题任务、编译运行用户代码、写入测试点与最终结果 |
| `apps/web` | Vue 3、TypeScript、Vite、Element Plus、Monaco | 公共题库、教学、考试、团队比赛、工单和管理后台 |
| `apps/api/migrations` | PostgreSQL SQL | 按版本执行并校验数据库结构变更 |
| `deploy` | Compose、Kubernetes | 容器化部署入口和参考清单 |
| `scripts` | Shell | 冒烟测试、沙箱镜像、题包示例和 Docker 清理 |

标准 Compose 部署还包含 PostgreSQL、Redis 和 MinIO：PostgreSQL 保存业务数据，Redis 承载判题队列、租约、通知和分布式限流，MinIO 保存题目包、题目资源和查重报告。

## 2. 业务边界

### 2.1 公共题目域

题目可来自公共／预备题库、授权团队私有题库及场次独立组题。正文、限制、标签、清单和题包按不可变版本保存；`problems.current_version_id` 指向当前版本。

题库写入经工单材料校验、在线组包或可选完整 ZIP 执行。场次草稿可独立编辑专用题目并整场送审，不自动公开为公共题。考试、比赛及提交保存明确的 `problem_version_id`；题库更新不自动替换场次绑定版本，仅草稿／退回状态允许明确采用最新版本。历史提交继续绑定原版本。

### 2.2 教学域

教学域管理课程、班级、成员、作业和校内考试。学生可以加入多个班级，并在课程空间内查看作业、考试和进度；教师和管理员负责教学资源、成绩报表和人工阅卷。

校内考试使用 `/exams/:id/*` 路由和考试专属接口。它与团队比赛共享 `EventWorkspaceHeader`、`EventProblemList`、`EventProblemPanel` 和排行榜组件，但通过独立适配器读取数据，不共享模型、权限判断或提交上下文。

学生显式进入考试时，事务锁定用户行并建立 `ExamAttempt`；提交和交卷复用用户锁，确保不能同时进入两场考试或在交卷后创建提交。鉴权后统一查询数据库中的活动考试，不依赖 JWT 角色快照或客户端存储。`ExamActivity` 记录考试行为，使用考试、用户、事件标识唯一键去重；原有 `AuditLog` 保留实际成功登录记录，入场日志关联其时间及 IP。

### 2.3 团队域

团队域管理团队资料、申请、成员、比赛和题单。团队成员角色为 `owner`、`admin`、`member`，比赛内容权限还受团队的 `contest_permission` 配置约束。

准入与职级管理采用 `handlers/team_join.go、teams.go → services/TeamAccess → domain/team.Repository → repositories/TeamAccess`。领域层定义权限和审批状态机，应用层编排用例，GORM 仓储集中实施团队行锁、账号状态检查和幂等写入。HTTP 层只转换输入、状态码和安全 DTO。大型 Handler 的其余业务仍按功能逐步迁移，不把本轮团队准入切片描述成全项目分层重写。

团队比赛使用 `/contest/:contestId/*` 独立路由。题单和比赛保存授权题目的关联及版本，比赛还支持场次专用题目，页面根据关联顺序生成 A、B、C 等场内题号，避免把公共题号当作场内标识。

### 2.4 提交与判题域

普通练习、作业、考试、团队比赛和团队题单都写入统一提交表，通过上下文字段区分归属。API 负责校验权限、时间窗、题目版本并创建任务；Worker 负责从排队状态推进到最终结果。

## 3. 核心数据流

### 3.1 工单与题目版本

1. 申请人按工单类型和资源权限填写题面、说明与材料；同题允许多份反馈。
2. 管理员校验所选材料并预览组包结果，不足则退回补充；也可上传完整 ZIP。
3. 执行校验 revision、当前题目版本和资源权限，题目行锁与事务保护并发。
4. 新增／替换产生不可变版本；归档只从后续目录和选题入口隐藏，既有引用保留。
5. 场次不自动采用新版本；草稿管理者明确选择更新，已开始场次和历史提交保持快照。
6. 处理记录、版本与对象写入保持一致，失败清理未引用对象并记录审计。详见 [工单流程](tickets.md)。

### 3.2 提交与判题

1. 客户端提交代码，API 根据练习、作业、考试、比赛或题单上下文完成权限校验。
2. API 在同一数据库事务中创建 `submissions` 和 `submission_outbox`，避免数据库成功但消息未发送。
3. 后台投递器把 Outbox 任务写入 Redis Stream `oj.submissions`。
4. Worker 消费任务并获取按提交编号划分的可续期 Redis 租约。
5. Worker 从 MinIO 下载该提交绑定版本的题包，在 Docker 沙箱中编译并逐测试点运行。
6. 最终状态、测试点结果和题目进度在一个 PostgreSQL 事务中写入。
7. Worker 发布轻量 Redis 通知，API 通过 `/api/submissions/:id/events` 推送 SSE；30 秒低频对账用于弥补瞬时通知丢失。

重判同样读取 `submission.problem_version_id`，不会因为公共题目后来更新而改变历史提交的输入数据。

## 4. 一致性与状态机

- 数据库迁移是嵌入 API 的有序 SQL 文件，执行记录保存在 `schema_migrations`，并使用 SHA-256 校验防止已执行迁移被改写。
- 迁移锁、台账创建和迁移执行固定在同一 PostgreSQL 连接，避免连接池导致锁和解锁落在不同会话。单个 SQL 迁移与台账写入同事务；失败仅回滚该文件，保留此前已提交迁移。兼容性 AutoMigrate 并不因此成为跨文件原子事务。
- API 拥有提交创建、上下文绑定和 Outbox 写入权；Worker 拥有判题状态推进和结果写入权。
- Worker 的 Redis 租约防止重复消费并支持崩溃后回收；基础设施故障按配置进行有限重试。
- 场次审核状态与时间阶段分开管理：草稿／退回可编辑，待审核锁定，通过后进入未开始／进行中／已截止，管理员确认后已完结。内部 revision 与送审次数分别维护，详见 [场次工作流](events.md)。
- 题目归档是逻辑删除，不破坏作业、考试、比赛和历史提交引用。
- 完整提交列表只用于展示；编辑器恢复通过 `/submissions/latest` 和上下文复合索引读取最近代码。

## 5. 排行与结果可见性

考试和团队比赛统一使用 OI、IOI、ACM 三种赛制，旧值 `score` 和 `penalty` 分别兼容为 IOI 和 ACM。

- OI：每题按最后一次提交计分；场次结束前参与者只看到“已记录”，不公开状态、分数、测试点或资源消耗；参与者不提供排行榜入口。
- IOI：每题取最高分；按总分、满分题数和最后有效得分时间形成稳定排序。
- ACM：按通过题数降序、罚时升序；通过前的有效错误提交每次增加 20 分钟罚时。
- IOI、ACM 可配置封榜。封榜期的榜单变化和提交结果仅管理员或组织者可实时查看，场次结束后自动公开。

脱敏在 API 返回、提交详情、SSE 和排行榜数据层统一执行，前端隐藏不作为安全边界。公开及后台排名在可重复读事务中计算；截止且排队、运行、待人工评分、系统错误均清空才返回 final_ready。手动刷新与进入页面更新榜单。奖项保存六位小数百分比，并按累计向上取整处理人数与并列。

## 6. API 与前端边界

- `/api/*` 为现有客户端兼容入口。
- `/api/v1/*` 与 `/api/*` 注册相同业务路由，新集成优先使用 `/api/v1`。
- Web 默认使用 `/api/v1`，业务请求已改用生成客户端 operationId；构建约束禁止页面重新引入直接 Axios 请求。传输拦截器和 SSE/页面离开时的 keepalive 保留专用实现，路径仍来自契约。
- 跨域来源由 `CORS_ALLOWED_ORIGINS` 控制，可信反向代理由 `TRUSTED_PROXIES` 控制。
- Bearer Token 只通过 `Authorization` 请求头传递；SSE 和私有文件下载使用带认证的 Fetch，不把 JWT 放入 URL。
- 前端路由按公共题库、课程、考试、团队和后台管理分区，具体页面见 [功能说明](features.md)。

## 7. 判题计量

每个测试点的 `time_ms` 来自沙箱进程组的 cgroup CPU 使用量，另设墙钟超时终止休眠或阻塞程序；`memory_kb` 使用 cgroup 峰值。内存超限通过 OOM 计数和 Docker 状态识别，不根据错误文本猜测。若已经观察到时间超限事件，清理阶段的退出信号不会覆盖该判定。

题目数据库中的时间、内存和输出限制为权威值；旧题包清单中的限制只作为兼容回退。

## 8. 可执行架构约束

- `internal/architecture`：领域、应用服务和仓储依赖方向；团队准入 Handler 不出现直接 SQL；API/Worker 绑定题目版本的字段一致。
- `internal/domain/team`：基础角色与团队三级职级的权限矩阵、审批状态机及重放规则。
- 路由兼容测试：两套 API 前缀具有相同方法、路径和业务 Handler。
- `scripts/check-architecture.mjs`：业务操作使用生成客户端；已收敛的团队页和提交详情不得增加硬编码颜色。其余历史页面按模块逐步收敛，不以全局样式替换掩盖差异。
- PostgreSQL/Redis 恢复测试验证 Outbox 补发、过期领取、Worker 租约接管、结果落库后 ACK 中断、迁移失败回滚与重试。使用隔离数据，不在生产执行故障注入。
