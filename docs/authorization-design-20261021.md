# 权限分层与项目落地记录

文档编号 AUTH-DESIGN-001 / 项目版本 1.1，日期 2026-10-21。维护责任人为项目维护者 TailingMing。本文对照提供的执行规范，记录实际实现、验收边界与回滚方式；运行时注册表以代码和 API 返回为准。

## 模型与取舍

保留学生、教师、管理员三种互斥的全站身份；出题者作为可叠加能力。课程管理员、助教和团队创建者、管理员、团员均为资源内职级，不能提升全站身份。用户已确认保留管理员身份并改为明确能力授权。

使用 RBAC 能力基线与资源属性/成员关系判定；当前没有需要多跳关系图的场景，不引入独立 ReBAC 存储。`authz.Engine` 是纯决策接口，HTTP、SQL 与审计不依赖图引擎。单学校部署不虚构 tenantId；未来多租户必须在身份来源、所有唯一约束与全部查询边界中共同加入租户条件。

与原规范有意调整的地方：

- 默认拒绝始终开启，不提供 `permitAll` 或关闭行级过滤的回滚开关。回滚恢复已验证的旧镜像和原规则。
- 角色授权可以并集；本人数据、课程管理范围、团队管理范围也是独立合法入口的并集。请求筛选条件、资源生命周期和隔离条件必须与该范围取交集，不能把所有合法授权互相取交集而使正常多角色用户失去权限。
- 不缓存决策。每个请求从数据库读取有效账号、当前角色、出题标志和版本，避免撤销延迟与缓存污染。前端每次重新登录/加载及超过 15 秒的导航刷新能力；前端提示不是安全边界。
- 内部业务一致性锁、考试准入和场次状态检查保留。并发写入前重验是事务一致性措施，不能按“禁止重复鉴权”删除。
- 非敏感模型查询无需盲目套同一 ORM 拦截器。敏感全局集合进入已命名 SQL scope；资源内集合在已授权父资源下附加父键；单资源、导出和对象存储下载先完成资源授权。

## 现状问题与改动

| 原问题 | 落地行为 |
| --- | --- |
| 路由散布 RequireRoles，新增接口可能漏闸门 | 显式登记 220 个 API 操作，两个 API 前缀共 440 个绑定；启动及 CI 双向检查，OpenAPI 同步 x-policy/x-access |
| 管理员直接在业务中放行 | 16 项全站能力逐项配置于 `internal/authz/grants.json`，6 项课程/团队资源能力走统一 PDP；新增代码不自动继承管理员权限 |
| 角色信息仅作为 JWT 单一声明 | 声明兼容 role，并增加 roles、perm_version、token_version；实际身份以数据库当前值为准，非法/空角色拒绝 |
| 教师拥有题目即可在列表看到其他团队使用该题的提交 | 提交 SQL scope 按实际课程、场次和团队归属授权；题目所有权只适用于独立练习提交 |
| 学生传 course_id 后绕开班级范围 | 作业和考试始终叠加 CourseWork scope；查询参数只能缩小范围 |
| 非学生提交路径缺少私有练习题授权 | 无作业/考试上下文时须满足公共题、合法团队范围或题目管理权限 |
| 离开团队后原作者可能继续管理团队题目 | 团队题目管理必须具有当前团队管理资格，或本人题目且仍有内容组织权限 |
| 公开题库通过率包含私有场次的提交 | 公开统计只统计独立练习，避免泄露考试/团队活动 |
| 权限变更与会话失效没有一致版本 | SQL 触发器维护 perm_version；改角色/出题权限下一请求生效；密码变更维护 token_version 并撤销旧令牌 |
| 最后一位管理员可被降级或自行注销 | 事务锁串行保护最后管理员，覆盖管理员编辑/删除及个人注销 |
| 教师无后台入口，页面按全站身份推断团队权限 | 全站入口读取后端 permissions；团队操作读取 can_organize；课程/班级读取 can_manage/can_admin，助教不显示设置编辑与成员增删 |
| 审计缺少拒绝与敏感读取 | 记录 401、403、认证后的资源 404，以及管理员访问、写入、提交详情、附件/题包/导出成功；页面显示判定原因与路由模板 |

## 分层资产

| 层 | 实现与契约 |
| --- | --- |
| L1 | `middleware/auth.go`：HS256、有效期、有效账号、2 秒身份读取超时；拒绝错误 Authorization 格式和非法角色。新旧令牌并存；旧令牌在首次密码变更后失效 |
| L2 | `authz/policy.go`：Context + policy + Resource → Decision；未知策略、身份或缺失资源拒绝。`authz/routes.go` 是操作注册表，资源 PIP 在 `handlers/authorization.go` |
| L3 | `visibility/scopes.go`：Courses、Classes、CourseWork、PreparedProblems、Submissions、PublicPractice；集合过滤先于分页/count。考试/比赛结果继续复用统一响应投影、封榜与 OI 隐藏规则 |
| L4 | `authorizationAudit` 写 audit_logs；仅记录策略、原因、路由模板、资源数字 ID、权限版本、状态和耗时；不记录原始查询串、令牌、代码或请求内容。失败写结构化 error 并增加指标 |

可查询入口：管理员 `GET /api/v1/authorization/policies`；后台“用户与权限 → 权限管理”显示能力及作用范围。“审计日志”显示 authorization.allow/deny 事件。

静态门禁检查管理员身份绕过和关键集合 scope。保留三个具名身份规则例外：管理员内置出题权不可单独移除，以及课程成员身份类型校验。角色名称的显示、存储、校验和学生考试状态机不属于特权绕过。

## 数据与敏感字段

- 源码仅在已过滤的提交范围返回；公开练习提交仍遵守原 `is_public` 规则，考试/团队提交不因复用公共题而公开。
- 密码散列、会话版本、对象存储密钥/对象路径保持不序列化。学生课程/班级列表在 SQL 投影中不读取邀请码。
- 题目包、测试点、场次附件、工单附件、人工阅卷、排行榜导出及 SSE 继续使用实际所属资源判断与已有封榜投影。测试覆盖相关已有流程。
- 所有 API 默认 `private, no-store`；未引入跨身份响应缓存。工作队列仅传提交 ID，Worker 取不可变题目版本，不授予用户侧查询能力。
- getById 已经完成资源 PEP 的入口不再套同一列表 scope；这是单资源检查与集合过滤的职责区分。

## 迁移与回滚

新增迁移 035–036：为 users 增加 perm_version、token_version 与版本触发器；不改历史迁移，不更改现有角色或成员关系。迁移 036 修正空库 SQL 安装遗留的课程职级 CHECK，允许课程管理员和助教，同时继续拒绝未知值；不改写历史迁移。两个字段默认 1，兼容原令牌与旧程序；角色/出题权限/注销更新增加权限版本，密码/注销更新增加会话版本。

发布前备份数据库和现有配置、记录应用/数据容器 ID、给旧镜像加回滚标签。候选源码经 Git 索引规范化字节导出，避免 Windows 换行符改变历史迁移校验和。先在独立 PostgreSQL 16/Redis/MinIO/应用容器验证，再运行正式迁移并仅替换 API、Worker、Web；数据容器和卷保留。

失败时恢复旧应用镜像。新增字段和触发器可保留，不需要逆向删列；旧程序不具备本次加强的撤销/范围规则，需明确回滚影响并尽快恢复修复版本。禁止修改历史迁移台账、重置生产数据或全局 Docker prune。

Git 提交/推送使用本机 Git 和用户已确认的 TailingMing 身份，按用户要求在远端验证通过后执行；部署源码树与最终提交的应用源码必须一致。既有四个脚本修改和 MEMORY.md 不包含在提交里。

## 验证与维护

自动化：能力矩阵（含空角色/未知角色/附加出题权）、课程/团队资源矩阵、两个 API 前缀注册表、OpenAPI 一致性、空库 SQL 安装课程职级与版本触发器、真实 PostgreSQL 跨班级/跨团队过滤与 count、旧令牌权限撤销、密码重置失效、最后管理员并发保护、敏感审计内容检查。保留全量考试、场次审核、工单、附件、导出和 Worker 恢复回归。

浏览器：`TestAuthorizationBrowserFixture` 仅绑定 127.0.0.1:18090；前端预览 127.0.0.1:4180；运行 `apps/web/tests/e2e/authorization-qa.mjs` 验证 1440×1100 与 390×844 的管理员能力表、跨团队管理、课程助教、团队普通成员及旧令牌权限撤销。产物存于忽略提交的 `tmp/authorization-qa/`。

指标：内部 `/metrics` 输出 `oj_authorization_decisions_total` 与 `oj_authorization_audit_failures_total`。`deploy/monitoring/authorization-alerts.yaml` 提供拒绝突增和审计失败规则；只有接入运维 Prometheus/Alertmanager 后才产生外部通知，不能把规则文件存在当作已配置通知。当前不承诺生产流量 P95 或 7 日基线，微基准与测试耗时不能替代压测。

新增能力工作流：先修改注册表/授权配置，确定父资源及 SQL 范围和敏感投影，再补正例/反例/跨范围用例，更新 OpenAPI 和前端能力提示，跑注册表门禁、完整测试和隔离容器验收，最后发布。增加角色映射只改配置；增加业务操作必须显式登记并完成资源授权。

本次没有实施多租户、多跳 ReBAC、动态策略编辑器或双人审批工作流；这些功能需要实际组织流程和独立数据模型，不能由“管理员”名称或开关自动推导。
